# 需求挖掘流水线（总控）

## Overview

把四个已验证的工具串成一条**带闸门的流水线**：`reddit-pain-mining`（找痛点+裁决）→ `gtrends-demand-scan` + KD 精评（搜索需求侧）→ `competitor-teardown`（竞品缺口+差评）→ 收钱验证。**每个阶段有明确 go/no-go 闸门，任一闸门失败就止损回机会池，不靠"再挖挖看"续命。**

**REQUIRED SUB-SKILLS:** 各阶段细节不在本文件重复，必须读对应 skill：
- 阶段 1-2：`reddit-pain-mining`（信号分类/receipts/记分卡/六级付费证据）
- 阶段 3：`gtrends-demand-scan`（词根/限流纪律/双通道判定）+ `scripts/kd_scan.py`（哥飞版精评）
- 阶段 4：`competitor-teardown`（官网 8 维度 + Trustpilot/Capterra/G2 三平台坑位）

## 流水线与闸门

| 阶段 | 内容 | 闸门 |
|---|---|---|
| P0 矿区选择 | 社区画像：about/new 密度、买家（付费者）密度、反方社区 | G0 主矿区信号密度成立 |
| P1 海捞+聚类 | top+new+**五组句式搜索（含第六类"系统间搬运"组）**+评论线程，30-50 receipts 聚 5-8 簇，百分制记分卡 | G1 ≥1 簇 ≥60 分且频率+付费意愿率 ≥60% |
| P2 深挖验证 | **跨年长跨度（≥3 年份独立 receipts）+ 反方社区 + 六级付费证据** | G2 跨年稳定 + 三源 ≥2 源闭合 |
| P3 搜索需求 | **先判渠道**：搜索型 → GTrends 词根 + SEO 生死簿 + **KD 精评收口**；触达型 → list-gate（不跑 KD） | 搜索型 G3 ≥3-5 词有真实量且 KD 可打；**触达型 G3′ 能列出 ≥50 家具体目标企业 + 触达路径** |
| P4 竞品拆解 | 官网 8 维功能矩阵（+ 客户软件栈与 API 可得性）+ **三平台差评聚类** | G4 存在可卡位层 + 定价锚成立 |
| P5 终评+形态 | 记分卡终评 + **形态分类器** + **定价锚** + **运维负担/事故等级** + 三问过滤 + 行业特有约束（如 PHI/YMYL）显式决策 | G5 全过 → 报告落盘 + 更新 AGENTS.md |
| P6 收钱验证 | landing page $1 smoke test → concierge → 收钱访谈 | G6 有人真付钱才算赢 |

P1→P2 只允许带 1-2 个簇过闸，防止全面铺开。

**第六类信号"系统间搬运"在 P1 最容易被静默丢掉**（它藏在"手工方案"里，不单列就不会被重新看见；实测回扫 8 个已归集落点得 146 条 source 命中，且最重的三条都是"抓到了但用错尺子"——失效点在判读/闸门层、不在海捞层）：句式清单读 `reddit-pain-mining` 的「采集方法」；这类 receipt **必须带两个字段——`软件栈`（A/B 软件名）与`搬运频率`（daily/weekly/monthly）**，否则 P2 判不出形态、P5 算不出定价。已归集语料回扫用 `python scripts/glue_scan.py`。

**P3 渠道分叉（2026-10-15 补，最重要的一条闸门修正）**——P3 前先判这个簇靠"搜索"还是靠"触达"获客，**判定顺序不能反**：

| | 搜索型 | 触达型（glue / 集成） |
|---|---|---|
| G3 用什么量 | GTrends 词根 + KD 精评（有量才成立） | **list-gate：能否列出 ≥50 家具体目标企业（名称+地区+"正在用 X 软件"证据）+ 有触达路径（冷邮件/老软件社区/行业论坛）** |
| 不成立的信号 | 无量 | **零搜索量是结构性特征，不是否决理由** |
| 变现 | per-event / 订阅 | 订阅（绑公司卡） |

判定依据见方法论的「两个获客通道」与 §4 阶段 2b 形态分类器（4 问：是否发生在两个既有系统之间 / 频率 / 客户是否已在这两个系统上花钱 / 两系统有无 API）。
**注意**：KD 只对搜索型成立——实测教训 8/9/10/11 全是搜索型纪律；拿 KD 筛 glue 型 = 结构性误杀（PT 每周 5-10 小时手工搬运的簇，Trends/KD 全程无声，但 Upwork 上已有人出钱买同类工具）。
**本项目当前立场=不走触达型**（一人售后负担+美国本地信任门槛+与 D 主攻冲突）：分叉是为了不误杀、也不误立项，不是为了开新通道。

## 压缩纪律（时间紧时唯一允许的操作）

**只能压缩采集样本量（少抓 30 帖），不能跳闸门、不能跳验证类型。** 实测压力场景下子代理会静默砍掉以下六项——它们每一项都对应一次真实踩坑，砍掉即返工：

1. **跨年长跨度验证**（P2）——top 列表全是戏剧帖，痛点必须靠搜索+评论+跨年测；单一时窗的高频可能是事件尖峰
2. **三平台差评**（P4）——只拉 Trustpilot 会漏 Capterra 的隐性收费主题和 G2 的沉默信号
3. **KD 精评**（P3）——预筛 KD 与精评落差可超 30 分（lease violation notice 预筛 1→精评 40.2）；跳过=生死簿失效
4. **价格现实检查**（P2 六级证据 L5/L6）——Etsy $1-3 实价 / 免费竞品覆盖，不做就会重犯"$29 幻想"坑
5. **词性分类**（P1）——服务采购/信息查询类信号不做产品，漏分类=把 lead-gen 当 SaaS 做
6. **渠道分叉判定**（P3 入口，2026-10-15 新增）——不判就默认用 KD 量一切，触达型（glue）簇会被零搜索量误杀。判据是"是否发生在两个既有系统之间 + 频率"，见上面的 P3 渠道分叉表

赶时间的正确做法：P1 少抓（top25+搜索 3 组）、P4 竞品站拆 5 家而非 11 家——但 P2 的五项验证与 P3 的渠道分叉一个不少，宁可砍样本不砍验证。

## P5 三维（形态 / 定价 / 运维）

P5 除了记分卡终评与三问过滤，必须显式产出这三项（细节读方法论 §4 阶段 2b-2e）：

1. **形态**：搜索型·事件型 / 搜索型·业务流型 / 触达型·业务流型 → 决定获客与变现
2. **定价锚**：`客户时薪 × 每天省下的小时 × 20 工作日 × 10-20%`，并与 Fiverr/Upwork 人力价锚交叉验证（数量级应接近）
3. **运维负担 / 事故等级**：`客户数上限 ≈ 每周客服小时 ÷ 单客户每周客服小时`；宕机是否等于客户业务中断（是=一人公司做不到，一票否决）

## 执行默认值

- **成本分层**：采集（.json/DOM 文本）派 `[secondary_model]` 池便宜模型；判读（聚类/记分卡/聚类判读）留主会话；截图是文本失败时的升级路径
- **通道**：WebBridge（127.0.0.1:10086），请求体写文件再 `curl.exe --data-binary`，evaluate 键名 `code`；Reddit 评论线程走 old.reddit.com
- **落盘**：原始数据 `reddit-data/{方向}_{source}_{date_HHMM}.json`；报告 `analysis_report_{方向}_{date}.md`（社区画像→receipts→记分卡→反对点→形态→下一步）；结论必须回写项目 AGENTS.md
- **反模式**（每个阶段收尾自检）：热门≠趋势、共鸣≠付费、骂得凶≠需求强、"无竞品"先核量、AI 先 receipts 后结论、社区先贡献后索取

## 常见错误

- **闸门当摆设**：G2/G3 不达标仍然"先做个 landing page 试试"——收钱验证（P6）只验证已过关的方向，不救验证不过关的方向
- **并行铺开多簇**：P1 出 5-8 簇全都想验证 → 必须记分卡排序只带前 1-2 簇
- **跳过 P0**：直接挖第一个看到的社区 → 付费者密度不够（如员工社区替代老板社区）会让付费意愿证据全失真
- **P6 前写代码**：闸门 G6 之前不开发，concierge/landing 先收钱
- **用 KD 闸门筛 glue 型机会**（2026-10-15 新增）：触达型需求零搜索量是结构性的，拿 KD/GTrends 筛它 = 结构性误杀。反向同样错：把触达型当 SEO 机会立项 = 得到零流量工具站。**先判渠道再选尺子**
- **拿共鸣数否决搬运型痛点**：glue 型证据没人点赞，10↑/8↑ 不代表弱——要看业务规模（营收/员工/客户数）与发生频率
